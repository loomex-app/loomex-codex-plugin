# Loomex plugin release and installation

The current package is a portable macOS arm64 Codex plugin. Public preview distribution and its exact paired release contract are documented in [public distribution](public-distribution.md). The release payload contains bundled JavaScript and a private Node.js 24.20.0 LTS runtime whose upstream archive is pinned by SHA-256. It does not use a GUI process's `PATH`, current directory, `PLUGIN_ROOT`, or undocumented plugin environment variables. After release verification, the installer derives `.mcp.json` from the signed template with absolute paths under the target user's stable `current` installation link. No build-machine home path is present in release bytes.

The 0.14.18 payload also packages `plugin/hooks/hooks.json`, its
`lifecycle-adapter.mjs`, and `plugin/runtime/bin/node`. The hook command binds
that runtime through `$PLUGIN_ROOT/runtime/bin/node`, so a plugin-only cache
layout resolves both the MCP server and lifecycle hook without a sibling
runtime directory, development Node, or `PATH` dependency. Codex
requires a user review and trust decision for plugin hooks after installation or
any hook update. The installer does not create or alter hook trust. See
[lifecycle hooks](lifecycle-hooks.md) for the fail-open lifecycle contract.

It adds the runner-owned connection projection and a content-addressed Connection resource.
The card displays only the browser authorization link and sign-in status, fetches organization
names as a separately retryable read, and binds quiet local status checks to the exact opaque login
flow. The browser handles account credentials and runner approval; no device code or password enters
the Codex card. Logout lets idle runner sessions quiesce before revoking credentials and refuses to cancel a running provider job.

`scripts/build-release.sh --production` requires a clean committed source revision and builds from a temporary `git archive` snapshot of that exact revision. It runs `npm ci`, type checking, tests, and the compiled bundle build. It downloads the pinned Node archive (or accepts `LOOMEX_NODE_ARCHIVE`), checks its digest, validates the plugin manifest and entrypoints, signs the runtime with hardened runtime options and the minimal JIT entitlement required by V8, and runs a post-sign JIT launch check. An unsigned development build may instead use `LOOMEX_NODE_RUNTIME_ROOT` only when its regular `bin/node`, `LICENSE`, binary digest, and reported version match the pinned runtime lock; production builds cannot use that local-runtime option. It rejects any payload containing the build machine's home path, emits a create-only deterministic release envelope, signs its canonical manifest, requires an `Accepted` Apple notarization result, and performs code-signature and Gatekeeper assessment. Production requires `LOOMEX_CODESIGN_IDENTITY`, `LOOMEX_NOTARY_PROFILE`, and `LOOMEX_MANIFEST_SIGNING_KEY`.

This Mac currently has zero valid code-signing identities. Production release and installation verification are therefore blocked. Nothing in this repository or CI output should be described as a signed, notarized, or release-verified production artifact until a Developer ID Application identity, Apple notarization profile, and offline manifest-signing key are provisioned and the production command succeeds.

For isolated tests only, `scripts/build-release.sh --unsigned-development` emits an artifact marked `developmentOnly`. The release envelope also contains `source-content.json`, a canonical `app.loomex.source-content/v1` manifest with SHA-256, size, and mode for every tracked and standard untracked source file present before compilation; `manifest.json` records its digest and entry count. Verification rejects an artifact that lacks this provenance by default. The `--allow-legacy-source-provenance` option exists only to inspect historical artifacts created before this contract; it cannot qualify a new candidate. Supplying `--source-root` additionally proves that the release matches the selected source contents. Installation additionally requires `--allow-unsigned-development` and `LOOMEX_ALLOW_UNSAFE_DEV_INSTALL=1`. Only explicitly reviewed unsigned preview candidates may be distributed through the public preview checkpoint; they remain development artifacts for isolated evaluation and must not be installed into a normal user environment. The public preview path does not weaken production signing gates.

The installer starts a bundled lifecycle manager with the release's pinned Node runtime. The release manifest binds the bootstrap runtime and manager hashes as well as the compressed payload; the shell launcher checks those hashes before execution. The manager verifies signature policy, project and platform provenance, payload digest, every file digest/mode/size, safe archive paths, production code signature and Gatekeeper acceptance, manifest component paths, and the signed launcher and marketplace templates before moving a staged directory into place. It then generates the local absolute launcher metadata and derives a stable marketplace descriptor at the installation base from the verified version template. Register the installation base as the private marketplace root; its generated `.agents/plugins/marketplace.json` points to `./current/plugin`, so Codex canonicalizing the registered directory cannot bind registration to a version that a later upgrade removes. The installer switches the `current` symlink atomically, refreshes the stable descriptor, and refuses to overwrite an existing version. Install `loomex` from `loomex-private` through the user-visible Codex marketplace flow.

Install and uninstall use an exclusive `.lifecycle.lock` and a durable versioned `lifecycle.json` journal at the installation base. Before a first installation creates that base, a narrowly named sibling bootstrap lock serializes that creation and hands off to the in-root lock. Stale-lock recovery is serialized and rechecks the exact owner under its recovery guard before it removes a stale lock. The journal records verified manifest, payload, and inventory digests before the stage is marked extracted, then advances through staged bytes, `current`, marketplace metadata, and ownership receipt phases with atomic replacement and directory fsyncs. Every resume at or after the bytes checkpoint recomputes the complete file/mode inventory against the journaled signed inventory before it copies a helper, switches `current`, or writes metadata. An incomplete stage is never trusted: resume removes it and verifies a fresh extraction. A completed journal remains until required cleanup finishes; `status` reports any retained journal as recovery-required. The ownership receipt retains the immutable signed inventory for every installed version, so `scripts/lifecycle.sh status`, `resume`, `rollback --version`, and `repair` return stable JSON and can verify retained bytes without Python, npm, or the source checkout. Matching incomplete rollback, repair, and uninstall operations reconcile through the same journal; a different operation or package is rejected. Uninstall permits already-removed journaled paths, but verifies any remaining target before deleting it and keeps its packaged helper until removal completes. It removes only versions named and inventory-verified by the receipt and never touches credentials. Codex marketplace registration is host-managed: the installer can create the local private marketplace descriptor, but cannot disable or remove the host registration, so remove that entry in Codex after a successful uninstall. `LOOMEX_PLUGIN_INSTALL_FAIL_PHASE`, `LOOMEX_PLUGIN_UNINSTALL_FAIL_PHASE`, and `LOOMEX_PLUGIN_LIFECYCLE_FAIL_WRITE` are test-only fault-injection controls used by `scripts/test-packaging.sh`.

After activating a new release, `scripts/lifecycle.sh prune --remove X.Y.Z --retain A.B.C` removes only the exact receipt-owned versions named by repeated `--remove` flags. The active version stays automatically; at least one different, verified rollback version must be named by `--retain`, and retained and removed names cannot overlap. Other unlisted versions remain installed. Prune refuses unowned paths, changed bytes, symlinks, and versions referenced by a live process. It records the ownership snapshot and exact plan in a v3 lifecycle journal, moves each removable version into an owned quarantine, deletes only its verified files, then atomically updates the v2 install receipt. `resume` completes the same plan after interruption; all other lifecycle mutations remain blocked until then. Older lifecycle readers reject an unfinished v3 prune journal, while completed prune leaves the normal receipt and rollback records readable. `LOOMEX_PLUGIN_PRUNE_FAIL_PHASE` is a test-only fault-injection control.

The package allowlist excludes Git metadata, environment files, credentials, secrets, development dependencies, npm caches, test output, logs, and coverage. The installer records the exact generated marketplace path in an installation ownership receipt and rejects preexisting, unowned metadata at that path. Uninstall validates the receipt, current version target, and generated descriptor before removing only the `current` link, exact version directory, receipt, and Loomex marketplace descriptor. It preserves unrelated files in the installation base and metadata directories. Disable/remove the plugin marketplace in Codex first so Codex does not retain a cached active copy.

CI runs `npm ci`, `npm run typecheck`, `npm test`, `scripts/test-packaging.sh`, and `scripts/test-node-runtime.sh`. Packaging tests use an explicit temporary install root, accept only an explicitly marked unsigned fixture, prove deterministic output and payload-tamper rejection, reject development/cache paths, validate absolute launcher binding, launch the MCP server and lifecycle hook from the plugin-only cached layout, keep a base marketplace registration valid across an upgrade, reject unowned marketplace metadata, and remove only receipted files. The runtime test downloads the official pinned archive, verifies its digest and reported version, and starts the compiled MCP server with that exact Node binary. An independent parallel CI job rebuilds and tests its captured source snapshot, then installs Codex CLI 0.146.0 on its disposable host, registers the stable installation base, installs the plugin through the real Codex command, checks discovery, and removes both entries.

The standalone production builder installs locked plugin tooling before checking the committed offline UI export. It requires no sibling frontend checkout. Regenerate and verify that export against the intended frontend revision before cutting the clean release commit. All packaged UI assets come from the immutable source snapshot; copied-package validation independently rejects retired UI implementations even when their asset digests are self-consistent.
