# Loomex custom UI design system

All five MCP Apps views—workflow browsing, run preparation, workflow authoring, run monitoring and human interaction—use the same design system. The source is the single inline stylesheet and reusable presentation classes in `assets/loomex-app.html`. `src/ui.ts` uses this same template for every resource; no network stylesheet, runtime UI framework or separate per-view theme is needed.

## Tokens

The stylesheet declares three layers in one place:

| Layer | Responsibility |
| --- | --- |
| Primitive | Green/red palette, spacing scale, font families, sizes and radii |
| Semantic | Canvas background/foreground, muted text, border, primary action, destructive action, error surface and focus ring |
| Component | Shell width/padding, section gap, card surface/padding and control height/border |

The shell is 720px wide with 12px gutters and 12px section gaps. System fonts, a 20px content heading, 8px card corners and 7px controls apply everywhere. Desktop controls are 36px square; coarse-pointer devices use 44px targets. Light and dark modes share semantic tokens.

A compact contextual toolbar identifies the current stage (browse, workflow details, setup, review, monitoring or response). There is no branded header or persistent connection footer. Refresh and connection information sit in the toolbar; run duration appears at the top right. An action bar appears only when there are actions. Run status, stage and current step share one wrapping line instead of a statistics grid. Started/completed timestamps live in a Run timing information tooltip. Missing or invalid timestamps do not invent a duration; terminal runs without completion timestamps omit it.

All actions use a consistent local SVG outline icon, an accessible name and a visually hidden text label. Labels preserve precise distinctions such as Start run, Review again and Retry exact response. Icons do not determine authorization or mutation arguments. Information buttons open text-only tooltips on hover, focus or tap; Escape dismisses them, keyboard focus remains on the trigger, and the tooltip remains available while hovered. Tooltips use `aria-describedby`, fit within the iframe and avoid covering their trigger. The interaction follows the [WAI tooltip guidance](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/). Essential authorization scope, questions and errors stay visible; only supplementary explanation moves into tooltips.

Waiting feedback comes from outstanding bridge requests and names the operation (preparing review, sending an answer, watching for an update). It is announced as status, with a small indeterminate spinner, never a fabricated percentage. The existing single-flight, idempotency and polling rules continue to own behavior. Reduced-motion preference disables spinner and status-dot animation. The header timer updates without rerendering questions or announcing every second.

## Shared components

| Component | Usage |
| --- | --- |
| `ui-stack`, `ui-grid`, `ui-section` | Vertical sections and responsive card grids |
| `ui-hero`, `request-copy` | Shared title scale and supporting copy |
| `ui-card`, `fieldset` | Review information and grouped questions using the same border, radius, surface and padding |
| `ui-label`, `ui-value`, `ui-caption`, `ui-badge` | Consistent information hierarchy |
| `ui-callout`, `notice`, `#summary` | Guidance, status, error and uncertain-result messages |
| `progress-steps`, `ui-list` | Named workflow stages and bounded summary, decision, review and result lists without invented percentages |
| `ui-disclosure` | Optional exact execution references |
| `.actions` and button variants | Contextual action bar, primary, secondary, destructive, hover, active, focus and disabled states |
| Form controls | Workflow inputs, workspace authorization, short/long answers, date, number, yes/no, choices, Other text and ratings |

Keyboard focus has a shared visible ring. Selected choices and ratings use the primary palette. Invalid controls and inline errors use the danger token. Locked answers retain their content and show a disabled state. Mobile visual order follows DOM/keyboard order. Every view sends the standard MCP Apps content-size notification after initialization and whenever the content size changes.

Single-question screens rely on the fieldset legend as the accessible question label. Presentational screens use the authored request title as their single section heading, with the presentation-kind label only as a fallback. The form suppresses that repeated title and keeps distinct supporting description or prompt copy while removing copies of the question and presentation summary. Repeated title/description/prompt copy is also collapsed without an input specification, and the question count appears only for batches. Normal question and authoring actions use `Continue`; the read-only action uses `Refresh`. Versioned implementation reviews keep their boolean response unchanged while labeling its choices `Accept` and `Request changes`.

## Presentation contracts

Human interaction and authoring views render optional `humanRequest.presentation` data only when it is the version 1 `progress`, `clarification` or `review` contract. Scalar fields are `question`, `stageLabel` and `summary`; bounded display lists are `changedFiles`, `artifacts`, `verification`, `limitations`, `priorRequirements`, `decisions` and `openQuestions`. Unknown fields such as raw `context.previousOutputs` are ignored. Current questions are removed from the open-question summary when they already appear as fieldset legends. Canonical stage names select the matching progress step using an exact case-insensitive comparison; other safe stage labels appear verbatim as a wrapping badge.

Run monitoring treats `execution.status` as authoritative. Active runs can wait for an update or request cancellation. `completed`, `failed` and `canceled` runs, plus compatible terminal spellings, disable and hide wait, cancellation and reason controls. Integrated and standalone monitors render a pending `humanRequest` inside the same shell with the shared typed-question, presentation and approval components. Explicit `Continue`, `Approve` or `Reject` actions call the matching interaction tool, consume a confirmed response, and then read the same run for its next authoritative state. Cancellation remains a separate action and never becomes an answer to the workflow question. During ordinary monitoring, its optional reason is collapsed; expansion and the reason draft survive status refreshes. An explicit cancellation screen or uncertain cancellation keeps the reason visible. The monitor shows the safe workflow name, stage, current step, locale-formatted timestamps and elapsed time when present. A version 1 `execution.result` may add summary, changed files, verification, limitations and artifact labels. Exact execution IDs stay in a collapsed reference disclosure.

Monitor reads and mutations remain bound to the mounted run. A pending request is actionable only when its nested execution ID matches that run and every supplied execution/request organization identity agrees with the monitored organization. Sequence numbers reject older snapshots and distinguish a same-sequence substitution from a newer authoritative successor. Every successful commit establishes an authoritative baseline with `loomex_run_get` before any human request becomes actionable; the commit receipt itself may contain only the new execution identity. Snapshot validation derives organization, request and reconciliation changes first, then applies them together only after every check passes. Refreshing or receiving a host notification for the same request preserves its local draft; a proven successor discards that draft. An authoritative resolved request, terminal state or higher-sequence successor also consumes an ambiguous interaction operation so its sealed answer can never attach to another question. Ambiguous mutations otherwise retain their exact answer, decision and idempotency key. Once the runner confirms a response, commit or cancellation, optional projection or follow-up read errors cannot make that accepted mutation retryable again. A non-terminal accepted cancellation becomes a distinct cancellation-requested state without another cancel action. Supported questions and approvals need no `ui/message` conversation handoff. While a visible active view has no pending question, single-flight waits continue with capped backoff even when `waitState` is absent. Valid active snapshots reset the consecutive-failure budget, while repeated failures pause automatic polling; a terminal state, human request or hidden view also stops it.

Large immutable results represented by a response spool are never partially decoded or accumulated in the UI. The `View results` action sends one stable `ui/message` request with one text content block, asking the conversation to read every page through `nextOffset` and verify `checksumSha256`; a host rejection remains visible as an error rather than success. Artifact labels remain plain text unless the authoritative result supplies a separately supported safe link contract; the UI does not turn workspace paths into links or commands.

Safe validation errors may show version 1 issue entries with a one-based step ordinal, fixed message and an allowlisted next-action label. Backend-authored node IDs and names are neither transported in that issue contract nor rendered. The top-level request/support reference remains optional. Error codes, unknown fields, transport details and raw result JSON are not rendered.

## Change rules and validation

Do not add selectors based on `data-mode` to the stylesheet or fork tokens per view. Choose an existing component or add a reusable semantic variant. Keep state and tool behavior separate from presentation: exact preparation bindings, read-only refresh, typed answers, approval decisions and immutable retries remain in the existing handlers. A failed authoritative result locks ordinary mutations until a successful refresh loads current state. Refresh stays available during that lock, while an uncertain mutation retains its separate exact-response retry.

The browser suite compares shared computed styles across all five modes in light, dark and mobile layouts, checks overflow, control targets, keyboard focus and resize notifications, and captures normal/error states. It also covers prompt deduplication, structured progress and acceptance review, typed responses, active and terminal monitoring, in-monitor question and approval cycles, stale run/request rejection, accepted-response read failure, paged-result handoff, bounded actionable errors, cancellation, integrated setup, canonical workspace binding, preparation and immutable retry. Set `LOOMEX_DESIGN_SCREENSHOT_DIR` to capture the visual matrix when running `npm run test:ui`.

The workflow browser uses compact divided rows within the shared typography, controls and responsive shell. Each row shows the name, optional description, status, published version and step count, followed by labelled `View` and `Prepare run` icon actions. `Prepare run` calls `loomex_run_setup` directly and changes the same app to the setup stage; it does not open a workflow-detail tool or add a preparatory conversation turn. Desktop rows keep metadata and actions on one line when space permits; narrow screens retain compact icon actions beside wrapping copy, with 44px targets for coarse pointers. UUIDs remain action identifiers rather than primary display text. Search uses one compact row with an accessible labelled form and pagination uses labelled navigation.

Workflow detail is a shared read view used after browser selection and for the explicit `loomex_workflow_view` authoring resource. The selected immutable version definition is authoritative even when the active version differs, and direct-authoring refreshes request that same version number. The view shows authored description, status and version; input titles, types and required state; bounded AI model/provider/effort configuration; and the declared execution policy with workspace-selection semantics. It renders at most the first 50 input requirements and 20 unique AI configurations, and states the displayed and total counts when more are present. Steps remain collapsed, render at most the first 100 bounded names and types, and state omissions without exposing raw JSON or identifier walls. Browser details return to the retained list page. Browser and direct authoring `Prepare run` actions both call `loomex_run_setup` and enter the integrated setup stage. Paged direct-authoring responses use the same safe conversation retrieval as paged browser responses without issuing another workflow or mutation call.

The run setup stage accepts only a bounded object schema with string, finite number, safe integer, boolean, or primitive enum fields. Required fields are validated before any tool call. Unsupported composition, references, nested structures, invalid workspace mappings, and unsupported types fail closed with an explicit conversation handoff. Schema defaults are not treated as user choices. `workspaceInputField` maps the runner-returned canonical grant path into the matching input without rendering a duplicate directory field.

Workspace authorization is a separate, explicit action. The UI sends the entered absolute path to `loomex_workspace_grant`, requires the verified workflow organization, and accepts only a canonical `workspace.path` returned for that organization and a valid installation with `host_user/v1`. That canonical path is then used for both `workspacePath` and the mapped workflow input. Only after authorization does `Review run` call `loomex_run_prepare` with the exact `selectedVersion.id`. The preparation response must carry a matching version 1 review projection before `Start run` is enabled.

Setup drafts survive validation and definitive tool errors. A timeout or ambiguous mutation keeps its immutable arguments and idempotency key, locks the displayed setup values, and exposes an exact retry. The preparation binding remains sealed through commit errors. When the runner definitively reports that this binding is stale, the Start action is retired and `Review again` requests a fresh preparation from the same sealed workflow version, inputs and canonical workspace. The fresh review has a new preparation identity and requires a separate Start click. A transient model-catalog failure keeps the existing reviewed preparation available instead of treating it as stale. Only a successful commit matching the requested preparation and execution policy with a verifiable execution ID advances to run monitoring; duplicate Start clicks are single-flight. The post-start model-context update includes the run ID and status only, never the confirmation key.

Integrated setup, preparation and start errors use the same versioned validation-issue presentation as other views. Issue cards survive redraws, retain the reviewed setup, and clear on the next attempt or successful refresh. Raw internal diagnostics are not rendered.
