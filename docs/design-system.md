# Loomex custom UI design system

All five MCP Apps views use the **frontend design system** from `frontend/packages/ui/src/styles.css` and its Button, Field, StatusBadge and Pagination components. The plugin does not own another palette. `assets/frontend-design-system.css` is a generated distribution snapshot, with source revision, input hashes, compiler version and output checksum in `assets/frontend-design-system.json`.

`src/ui-template.ts` verifies and inlines that snapshot into every resource. The browser harness uses the same renderer. Installed views require no frontend checkout, React runtime, external stylesheet, font download or network permission. The local stylesheet in `assets/loomex-app.html` owns only the compact iframe layout, domain-specific choice/rating widgets, and accessibility adaptations.

## Foundations and components

The frontend UI currently uses a dark canvas and card surfaces, white primary actions, transparent secondary actions, teal selection/success, violet running/draft, orange waiting and pink failure/destructive states. Its neutral theme factory exposes a light mode, but its actual UI component stylesheet is dark; embedded views deliberately use the shipped dark component design rather than inventing an inconsistent light variant. A future frontend light design must be exported and validated together with its components.

Typography inherits the frontend Inter/system and JetBrains Mono/system font stacks. No web fonts are fetched. Cards use the frontend 12px radius; controls use its 8px radius and shared transition/state styling. The iframe retains compact 12px gutters, a 720px maximum width and 12px section gaps. Icon targets are at least 36px on desktop and 44px on coarse pointers; keyboard focus stays visible even where the frontend input class suppresses the native outline. Small muted labels use the frontend gray-400 token for contrast on dark cards; execution waiting states use its orange waiting color.

## Updating the shared export

From the plugin root, with frontend dependencies installed using its pinned package manager:

```sh
npm run design:sync
npm run design:check
```

For a separate frontend checkout use `node scripts/sync-design-system.mjs --frontend /absolute/path/to/frontend`. Review and commit the generated CSS and provenance together. The export compiles the actual frontend CSS and discovers utility candidates from the plugin template and canonical frontend button/status variants. It rejects network imports and resource URLs. Do not edit the snapshot manually. Normal plugin release builds verify the packaged hash without requiring a sibling checkout; design changes additionally require the explicit upstream sync check.

A compact contextual toolbar identifies the current stage (browse, workflow details, setup, review, monitoring or response). There is no branded header, visible connection control or persistent connection footer. Refresh sits in the toolbar; run duration appears at the top right. An action bar appears only when there are actions. Run status, stage and current step share one wrapping line instead of a statistics grid. Started/completed timestamps live in a Run timing information tooltip. Missing or invalid timestamps do not invent a duration; terminal runs without completion timestamps omit it.

Actions use consistent local SVG outline icons and accessible names. Review/Submit answer(s) and Start run retain visible text; familiar navigation and refresh icons may use visually hidden labels. Labels preserve precise distinctions such as Start run, Review again and Retry exact response. Icons do not determine authorization or mutation arguments. Obvious action icons do not repeat their accessible names in hover tooltips. Information buttons exist only when they explain real data, such as exact run timestamps; those tooltips open on hover, focus or tap, use `aria-describedby`, fit within the iframe and dismiss with Escape. Essential authorization scope, questions and errors stay visible.

Waiting feedback comes from outstanding bridge requests and names the operation (preparing review, sending an answer or sending a run to chat). Workflow list, search, pagination, detail and setup reads place an `aria-hidden` skeleton over the existing content and reserve the full app and embedding-host height. A visible status inside that reserved region receives focus without scrolling while the former controls are hidden, then focus returns to the initiating control after success or error. The containing region exposes `aria-busy`; its local status supplies the loading announcement without adding a second global activity row. Single-flight and idempotency rules continue to own mutations. The UI never schedules run polling; only the presentation clock has a timer. Reduced-motion preference disables spinner, status-dot and skeleton animation. The header timer updates without rerendering questions or announcing every second.

## Shared components

| Component | Usage |
| --- | --- |
| `ui-stack`, `ui-grid`, `ui-section` | Vertical sections and responsive card grids |
| `ui-hero`, `request-copy` | Shared title scale and supporting copy |
| `ui-card`, `fieldset` | Review information and grouped questions using the same border, radius, surface and padding |
| `ui-label`, `ui-value`, `ui-caption`, `ui-badge` | Consistent information hierarchy |
| `ui-callout`, `notice`, `#summary` | Guidance, status, error and uncertain-result messages |
| Header stage badge, `ui-list` | Current authoritative stage and bounded review/result lists without an invented workflow sequence |
| `ui-disclosure` | Secondary run references and bounded workflow steps |
| `.actions` and button variants | Contextual action bar, primary, secondary, destructive, hover, active, focus and disabled states |
| Form controls | Workflow inputs, workspace authorization, short/long answers, date, number, yes/no, choices, Other text and ratings |

Keyboard focus has a shared visible ring. Selected choices and ratings use the primary palette. Invalid controls and inline errors use the danger token. Locked answers retain their content and show a disabled state. Mobile visual order follows DOM/keyboard order. Every view sends the standard MCP Apps content-size notification after initialization and whenever the content size changes.

Single-question screens rely on the fieldset legend as the accessible question label. A batch keeps every control mounted but shows one question at a time, with labelled previous and next arrow actions and a `Question n of total` status. Earlier questions have no persistent review action. On the last question, `Review answers` with the eye icon occupies the next-action position in the stepper. Moving forward validates the current question; moving back never erases a draft. Stable authored question IDs remain attached to the final answers. Presentational screens use the authored request title as their single section heading, with the presentation-kind label only as a fallback. The form suppresses repeated title, description, prompt and question copy. Versioned implementation reviews keep their boolean response unchanged while labeling its choices `Accept` and `Request changes`.

Typed responses have an explicit review boundary. `Review answer(s)` validates the complete form and opens a safe, readable preview for text, long text, date, rating, boolean, radio, checkbox and Other values. The visible preview heading receives focus without scrolling so focus never remains in hidden question content. Edit actions return to the exact question without remounting controls. Only `Submit answer(s)` creates the mutation. Empty controls and schema defaults never count as consent. A locked ambiguous response retains the exact reviewed payload and operation ID.

## Presentation contracts

Human interaction views render optional version1 presentation data from explicitly declared workflow inputs. Clarification questions omit generic accumulated-context disclosures and redundant request titles. Their explicit summary is helper text associated with the question control. Review views retain deliverable summaries, changed files, checks and limitations. The current stage appears in the shared header; stage labels do not infer a fixed path or completion percentage.

Run monitoring treats `execution.status` as authoritative. Active snapshots offer `Follow in chat`, explicit `Refresh run` and a separate cancellation action. `completed`, `failed` and `canceled` runs, plus compatible terminal spellings, hide active-run actions. Integrated and standalone monitors render a pending `humanRequest` only when its authoritative `answerChannel` is `ui`; chat-channel singular long-text requests stay in chat and never produce a textarea card. Unsupported requests surface a compatibility error without answer controls. Cancellation never becomes an answer to a workflow question. Its optional reason stays collapsed during ordinary monitoring, and its draft survives explicit refreshes. The monitor shows the safe workflow name, meaningful observed stage/current-step details, locale-formatted timestamps and elapsed time when present; it does not expose private reasoning or infer a completion percentage. A version 1 `execution.result` may add summary, changed files, verification, limitations and artifact labels. Exact execution IDs stay in a collapsed reference disclosure.

Monitor reads and mutations remain bound to the mounted run. A pending request is actionable only when its nested execution ID matches that run and every supplied execution/request organization identity agrees with the monitored organization. Sequence numbers reject older snapshots and distinguish a same-sequence substitution from a newer authoritative successor. Snapshot validation derives organization, request and reconciliation changes first, then applies them together only after every check passes. Refreshing or receiving a host notification for the same request preserves its local draft; a proven successor discards that draft. An authoritative resolved request, terminal state or higher-sequence successor consumes an ambiguous interaction operation so its sealed answer can never attach to another question. Once the runner confirms a response, commit or cancellation, later display or handoff failures cannot make that accepted mutation retryable again. Chat-channel interactions render a small routed handoff with no editable controls and no repeated full question; the authoritative chat question is collected in the conversation.

After a verified run start or run-backed response, the app consumes the mutation before chat handoff. If the host advertises both text capabilities and the runner supplied `details.followContinuation.receipt`, it sends an acknowledged `ui/update-model-context` request followed by an acknowledged `ui/message`. Context is a factual `loomex/chat-continuation/v2` lifecycle record, rendered as a labelled fenced JSON block, with the exact run, trigger, accepted request ID/status where applicable and opaque runner receipt. The separate `$loomex-follow` command is formatted by the canonical hooks formatter for both the sent message and manual copy: its first line is the bare routing command, followed by the receipt comment and compact fresh-read instructions. A missing receipt stays on the manual fallback and never sends an activatable generated message. The conversation then follows authoritative `nextAction`, bounded waits and the new request's answer channel: one UI view for a newly pending UI request, a headless chat get for a chat request, or an actionable compatibility error for an unsupported request. This avoids duplicating generic instructions and tells chat that the earlier form has been submitted. Neither channel includes preparation secrets, workflow-authored text or user answers. Success says only `Sent to chat`; it does not claim that monitoring has begun. Failure offers `Retry chat handoff` retaining the same receipt, which cannot repeat the accepted mutation, and an expandable manual command with the same accepted-request context. Missing host capabilities use that manual fallback.

Display and data tools are separate. `loomex_workflows_view`, `loomex_run_view` and `loomex_interaction_view` own app resources; their corresponding data tools remain headless. Explicit in-app refreshes use the data tools once. The app never calls model-only `loomex_run_wait`.

Large immutable results represented by a response spool are never partially decoded or accumulated in the UI. The `View results` action sends one stable `ui/message` request with one text content block, asking the conversation to read every page through `nextOffset` and verify `checksumSha256`; a host rejection remains visible as an error rather than success. Artifact labels remain plain text unless the authoritative result supplies a separately supported safe link contract; the UI does not turn workspace paths into links or commands.

Safe validation errors may show version 1 issue entries with a one-based step ordinal, fixed message and an allowlisted next-action label. Backend-authored node IDs and names are neither transported in that issue contract nor rendered. The top-level request/support reference remains optional. Error codes, unknown fields, transport details and raw result JSON are not rendered.

## Change rules and validation

Do not add selectors based on `data-mode` to the stylesheet or fork tokens per view. Choose an existing component or add a reusable semantic variant. Keep state and tool behavior separate from presentation: exact preparation bindings, read-only refresh, typed answers, approval decisions and immutable retries remain in the existing handlers. A failed authoritative result locks ordinary mutations until a successful refresh loads current state. Refresh stays available during that lock, while an uncertain mutation retains its separate exact-response retry.

The browser suite compares shared computed styles across all five modes in light, dark and mobile layouts, checks overflow, control targets, keyboard focus and resize notifications, and captures normal/error states. It also covers question navigation, back/edit draft retention, per-question validation, answer review, the review-to-mutation boundary, exact retries, zero automatic run polls, acknowledged chat handoff and manual capability fallback. Existing coverage retains prompt deduplication, structured progress, stale run/request rejection, paged-result handoff, bounded actionable errors, cancellation, integrated setup, canonical workspace binding and preparation sealing. Set `LOOMEX_DESIGN_SCREENSHOT_DIR` to capture the visual matrix when running `npm run test:ui`.

The workflow browser uses compact rows with name, useful description, status, version and View/Prepare actions. Its bottom pagination bar is always present for a verified list, including empty and single-page results. The frontend-owned Pagination component supplies the semantic structure, class names, dimensions, page-size options and control states; the offline plugin adapts that structure to cursor history. It shows `Page n · x workflows`, Previous and Next, and a labelled page-size selector. It never invents a total or unsupported page jump. Query and page-size changes reset cursor history. Boundary controls remain visible but disabled; delayed reads preserve layout and restore navigation focus after rendering.

Workflow detail is a shared read view used after browser selection and for the explicit `loomex_workflow_view` authoring resource. The selected immutable version definition is authoritative even when the active version differs, and direct-authoring refreshes request that same version number. Its purpose-first heading keeps Back and Prepare beside the workflow identity when space permits. The body uses short Inputs, AI and Steps sections: authored input descriptions take priority over repeated schema types, AI rows show only provider/model/effort, and steps show names without raw node types. It renders at most 12 inputs, eight AI configurations and eight step names, then states the displayed and source counts without suggesting a fabricated total. A declared `host_user/v1` policy becomes one readable line; exact authorization review remains in preparation. Browser details return to the retained list page. Browser and direct authoring `Prepare run` actions both call `loomex_run_setup` and enter the integrated setup stage. Paged direct-authoring responses use the same safe conversation retrieval as paged browser responses without issuing another workflow or mutation call, and require all pages plus checksum verification before interpretation.

The run setup stage accepts only a bounded object schema with string, finite number, safe integer, boolean, or primitive enum fields. Required fields are validated before any tool call. Unsupported composition, references, nested structures, invalid legacy workspace mappings, and unsupported types fail closed with an explicit conversation handoff. Schema defaults are not treated as user choices. New workflows do not need a directory input: workspace belongs to task setup. Existing `workspaceInputField` mappings remain readable and map the runner-returned canonical grant path into the matching legacy input without rendering a duplicate directory field.

Workspace selection and registration are part of preparation, without a separate Grant button or success screen. A known task path or explicit override with no authored inputs goes straight through workspace verification and preparation to the review in the same card. Otherwise the form collects workflow inputs and a missing or changed path, then `Review run` completes both prerequisites. Workspace management remains available as an advanced tool, not a normal-run stage. Registration alone cannot execute; the runner also requires durable authorization for the exact committed preparation.

The flow verifies the returned canonical `workspace.path`, workflow organization, installation and `host_user/v1`, then prepares the exact selected version. Ambiguous registration/preparation retains its own sealed arguments and key and waits for an explicit retry. Only an accepted registration continues to preparation; duplicate initial notifications must not start a second pipeline. Editing setup preserves drafts and invalidates the previous review when facts change. No additional directory input is needed for a known current project.

The preparation response must carry a matching version 1 review projection before `Start run` is enabled. Its purpose-specific review shows the verified workflow name, pinned version, organization and `This Mac` once in one metadata line and keeps workspace, providers, and authored inputs compact. The workspace/policy explanation is part of the explicit prepare confirmation contract and is not repeated as a card in the review. The sealed binding and exact policy stay enforced internally instead of becoming a duplicate developer-facing reference block. Confirmation keys, binding digests and installed-provider internals remain hidden; idempotency and sealed retry behavior remain in the action handlers.

Setup drafts survive validation and definitive tool errors. A timeout or ambiguous mutation keeps its immutable arguments and idempotency key, locks the displayed setup values, and exposes an exact retry. The preparation binding remains sealed through commit errors. When the runner definitively reports that this binding is stale, the Start action is retired and `Review again` requests a fresh preparation from the same sealed workflow version, inputs and canonical workspace. The fresh review has a new preparation identity and requires a separate Start click. A transient model-catalog failure keeps the existing reviewed preparation available instead of treating it as stale. Only a successful commit matching the requested preparation and execution policy with a verifiable execution ID advances to the chat handoff; duplicate Start clicks are single-flight.

Integrated setup, preparation and start errors use the same versioned validation-issue presentation as other views. Issue cards survive redraws, retain the reviewed setup, and clear on the next attempt or successful refresh. Raw internal diagnostics are not rendered.


## Shared information hierarchy

Every view uses one compact header, a task-focused body and a predictable action area. The header identifies the current view or workflow without duplicating the body's main heading. A human interaction may show its authoritative current stage; there is no fixed Idea/Clarify/Build/Review strip or inferred overall completion percentage. Question position describes only the known batch.

In clarification forms, the question is the primary label. A separate request title is not repeated above it. Explicit presentation summary text provides associated helper content; the renderer does not split arbitrary authored sentences. The generic Requirements context disclosure is omitted from questions. Review-specific deliverables, checks and limitations remain visible; underlying history is unchanged.

Previous/Back actions stay left and primary actions right. Review answer(s), Submit answer(s) and Start run have visible text and an icon; familiar navigation and refresh controls may use icons with accessible names. Loading and handoff confirmation remain inline in the current card. Typed validation, answer previews, keyboard focus, exact mutation retries and chat-owned monitoring remain the same.
