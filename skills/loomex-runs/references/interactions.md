# Typed human responses

Use the exact pending request ID from the selected run's authoritative snapshot and validate request, run, organization and schema identities. The runner's `humanRequest.answerChannel` is authoritative: it is `"chat"`, `"ui"`, or `"unsupported"`. For `"unsupported"`, surface the authoritative compatibility error and pause; do not render a fallback form or reinterpret its schema. Follow the fresh run snapshot's `nextAction`; never unconditionally open an interaction view.

For `answerChannel: "ui"`, call `loomex_interaction_view` once. It fetches the current complete schema itself, so do not precede it with `loomex_interaction_get`, open a run view, or duplicate the form in chat. Remember its unresolved request ID and exact `viewSessionId` when returned. Reopen only when the user explicitly asks, carrying that exact session ID when the tool supports it. The card owns navigation, draft, preview and submission.

For `answerChannel: "chat"`, call `loomex_interaction_get`. Its model projection returns the exact singular question, response schema, answer channel and schema digest needed for a headless answer while omitting unrelated execution history. Read those fields from `structuredContent.data`; do not look for a canonical UI payload on this headless tool. Chat long-text requests are singular: do not combine them with another question or manufacture a batch form. Present the question in chat without a textarea card. A direct, clear user answer may be submitted immediately. A request to research, discuss, inspect a file/tool, draft alternatives, or otherwise continue the conversation is not itself an answer. When an answer is synthesized across multiple exchanges, tools or files, give a concise proposed answer and obtain confirmation before submitting.

`inputSpec` owns text, stable IDs, type, choices, Other behavior and rating bounds; `responseSchema` owns payload structure. Dates are YYYY-MM-DD; ratings respect supplied integer bounds; false is an explicit value, not missing. Other requires its text. Send stable question/option IDs and values, not labels as identifiers. Never invent defaults or collect secrets.

Immediately before `loomex_interaction_respond`, take a fresh `loomex_interaction_get` for chat (or use the UI-owned submission path). Verify the unresolved request's exact request/run/organization/schema identity and revision against the sealed answer. Pass its actual `schemaDigest` as `expectedSchemaDigest`; if it is missing or changed, stop submission and refresh the question instead of inventing a digest. Use `loomex_interaction_respond` for typed answers and `loomex_interaction_decide` for approval/rejection; approval is a distinct decision. Retain one idempotency key and the exact answer after ambiguity. UI submissions own their mutation and must not be repeated from chat. Verify an accepted receipt identifies the intended request/run and resolved status without error; otherwise reconcile through reads. Never replay an accepted answer.

The interaction's exact `requestId` determines the response route. Do not pass a `requestType`, routing category, or `inputSpec.inputType` such as `long_text` to `loomex_interaction_respond`. For list filtering only, `loomex_interactions_list.interactionCategory` accepts `human`, `approval`, or `plugin_agent`; it is separate from the question's input type.

After an accepted response, or exact authoritative reconciliation proving acceptance, resume the same run using [monitoring](monitoring.md), unless the user explicitly asked for answer-only behavior. Clear the remembered request/view session before continuation; the acceptance receipt only triggers a fresh `loomex_run_get`, and the snapshot's live `nextAction` controls the next step. Handoff failure does not revoke acceptance. Already resolved or terminal requests cannot receive another answer; report current state and use read-only continuation.
