# Active-chat authoring

Conversational creation and editing happen in the current chat. First read `loomex_builder_catalog`, then construct the candidate definition only from its canonical `authoringContract` and supported node, provider, field, and graph schemas. Canonical nodes use top-level `key`, `name`, `config`, `inputs`, `inputSchema`, and `outputSchema`, and the graph uses `transitions`. Never submit browser-only node `id`, nested `data.config`, or `edges`. Preserve the user's initial authoring request as source material; do not replace it with an invented generic prompt. Preserve requested provider, model, and reasoning choices on the applicable catalog-defined nodes. A node's provider configuration stays distinct from any other node or workflow metadata. New secret-reference mappings are unsupported.

Validate every candidate with `loomex_workflow_validate` before saving it. When validation returns structured `issues`, repair only the cited definition paths while preserving the user's requested behavior and validate the whole candidate again. Do not infer a different human-input type from a misplaced-field error. Allow at most three automatic repairs after the initial failed candidate. Stop earlier if the same candidate and issue set recur, or if a repair would require a product decision the user has not made. Ask for focused guidance, retain the candidate and issues, and start a fresh repair cycle only after that guidance arrives. If validation history is unavailable after context compaction, do not silently reset the budget. Validation failures are definition feedback; transport, authentication, catalog, permission, and backend failures are operational errors and must never consume a repair attempt or be "repaired" by inventing a definition. Do not save a known-invalid candidate.

On validation success, save the returned normalized `workflow` exactly, not the pre-validation candidate. For a new workflow, call `loomex_workflow_create` once with `name`, optional `slug`, that normalized `definition`, optional `notes`, and one idempotency key. That saves the workflow and its draft atomically; do not create an empty workflow and then issue a second update for the same candidate. If create or update returns `NETWORK_AMBIGUOUS`, call `loomex_workflow_operation_get` with the exact operation and original idempotency key. A completed receipt is authoritative, pending means wait and read again, and not-found permits retrying only the exact original mutation and key. Never reconcile an authoring mutation by matching a workflow name or slug. After a completed save, read the exact `workflowId` at `version: "draft"` with `loomex_workflow_get`; verify the draft identity, revision, and saved definition against the normalized candidate before reporting success. If readback is unavailable or differs, report the save as unverified and reconcile the exact operation; do not create or update again with a new key. A saved draft does not mean published or active.

For an edit, read `loomex_workflow_get` with `version: "draft"` when a draft exists (otherwise use the selected published version), preserve every untouched field, and apply the requested change to a candidate definition. Immediately before the save, read that same draft again and use its current draft revision as `expectedVersion` in `loomex_workflow_update`. A changed revision requires reconciliation and a re-derived candidate; never overwrite it. Validate the re-derived candidate before the update.

After verified readback, make one explicit compact `loomex_workflow_view` call for the saved workflow and version when the task has a local cwd and a visual review is appropriate. If the host cannot render a view or has no local task cwd, use the verified `loomex_workflow_get` result for a concise headless summary. The summary is a saved-draft review, not a publishing, activation, or run request.

Workspace selection belongs to execution setup, not active-chat authoring. Do not add a project-directory input or `settings.workspaceInputField` to new workflow definitions. Existing stored versions that already contain that mapping remain valid and readable; preserve unrelated legacy fields during an edit unless the requested change requires updating them. When a workflow node needs the selected execution workspace as text, use the optional catalog-supported mapping `{ "source": "execution_context", "value": "workspace.path" }` on that node field. Omit it when no node needs the path.

`loomex_builder_prepare` and `loomex_editor_prepare` remain only for an existing execution-backed compatibility integration. Their returned workspace/provider/`host_user/v1` binding still needs explicit review and the matching commit before that compatibility session starts. Never use either prepare/commit path to start a new active-chat authoring request. If an existing builder or editor session ID is supplied or recovered, use headless `loomex_builder_get` to observe it and the matching response/finalize tools to recover that exact session. Do not turn it into a new conversational route.

Saving a draft does not authorize publishing, activation, or execution. Each requires its own requested scope.

## Workflows that author workflows

An executing AI node can propose a canonical definition, but it cannot call Loomex MCP tools or inherit this conversation's tool authority. Use an explicit backend tool node with `config.tool` set to `workflow_draft_create` or `workflow_draft_update`. Create accepts a name, optional slug/notes, and definition. Update accepts the workflow ID created by the same execution, its expected draft revision, optional notes, and definition. These operations validate and save a draft only; they never publish, activate, execute, or delete it.

Keep proposal AI nodes read-only with a strict JSON output schema. Map their output into the deterministic tool node, route `validation_failed` issues back to the proposal loop, and preserve the returned workflow ID and draft revision through explicit mappings. Do not rely on provider memory or a model-emitted repair counter. The backend draft tool returns `repair.canRetry` from durable, execution-scoped mutation receipts: it allows three automatic repairs after the initial validation failure, stops on a repeated candidate and issue set, and resets only after completed human repair guidance. Route the gate from that trusted field; operational failures do not enter the definition-repair loop. User clarification rounds remain unbounded.
